# Developing Nuée

Every calculation is plain R in `moteur/R/`, commented in French, so that the person using the
application can read and correct it. The interface is an Electron window with dockable panels,
pop-out windows and Plotly plots, talking to a local R server.

## Layout

| Folder | What it holds |
|---|---|
| `moteur/R/` | The engine: preprocessing, NIPALS PCA/PLS with missing values, cross-validation, OPLS, statistics, prediction, HCA, new analyses |
| `moteur/serveur.R` | Local HTTP server (httpuv) answering the interface's JSON requests (`reajuster`: a model refitted without some observations, as the AIC selection's Fit this model, or with a CAR1 autocorrelation, Fit with CAR1; `condition_observations`: how many ticked observations a condition keeps, for New model's Observations tab; `ajuster_et_garder` keeps a definition with the observations its condition gives; `series`: a refused trend option, such as seasons by month without dates, leaves the plot and is returned as `tendances_erreur`; `table_a_joindre` and `ajouter_colonnes`: Edit › Add columns from a table, the table in any format File › Open reads, `tableau_a_joindre`: a table with its key columns as written, or a project's data; pasted cells kept in a file of the session; undone by Ctrl+Z; `resumer_groupes`: Edit › Summarize by group, a new unsaved project; `raster_infos` and `ajouter_raster`: Edit › Add raster values, what each file is (or why it is refused, without stopping the others), then the values added, one undo step, `fichiers_raster_demande` reading the files' array that jsonlite makes a data.frame; `coefficients_modeles` and `exporter_coefficients`: regressions side by side; `puissance_tendance`: the trend power, kept with the model; `moyennes`: the adjusted means, kept with the model; `resultat_regression` lists a regression's qualitative variables, `qualitatives`, for the view; `figure`, `figure_enregistrer`, `figure_supprimer`: the figures for publication (figures.js), kept in `p$figures` as `{ id, titre, contenu }`, `contenu` the JSON text only the interface reads, saved with the project and left alone by undo, as the documents are; the living reports, etapes.R: a file opened records its source, each data-changing request notes its step through `changer_projet` or `noter_etape`, `etapes`, the source and the steps, `retirer_etape` and `mettre_a_jour`, its preview with `apercu`, each one undo step; `ouvrir` with `nom` and `lecture_seule`, an old version (interface/versions.js) under its name, `resume_projet`'s `lecture_seule` its source, oid and date, never saved over the temporary file it was read from and no longer read-only once saved elsewhere, or with `cache`, a project left out of `etat` while What changed fits its models; neither ever read from a file; merging two versions, fusion.R: a `.nuee` opened is copied first into the session's temporary folder and read from the copy, and `enregistrer` writes the file there first, then copies it into place (`copie_fichier_lu`, in `fichier_lu$copie`; `ranger_copies` keeps only the one in use and the base an undone merge would bring back, `fermer_projet` deletes them), never next to the user's file; `enregistrer`'s `auteur`, the name written in `p$nuee$auteur`; the save conflict (409) says `fusion` when a copy is kept; `fichier_change`: size and date, then the content (`meme_empreinte`) against the copy, a date alone changed refreshing `fichier_lu`, and who wrote the file from its `nuee` header read in its bytes (`entete_projet`); `fusionner` (three files, or `projet` with the kept copy as base and its file as theirs), `fusionner_finir` (the merged project to a file, its `auteur` written as `enregistrer` writes it, or in the session's place: one undo step, `memoriser`'s `fusion`, whose documents, figures and file state Ctrl+Z gives back while they haven't changed since; refused when the project changed since `fusionner`)); `predire` and `predire_fichier`: a model of the session predicts on the project as it saw it, with the definition of its fit (`pour_predire`, atelier.R: `projet_tel_ajuste`), so a new order of categories since leaves its predictions as they were (a forest's, boosted trees' or a tree's qualitative X, an LDA's indicators), a hierarchical model's base models too, each refused as `modele(id, TRUE)` refuses it when a category it saw was renamed or removed; console.R logs the prediction on that project; R-code models (code.R): `code_approuve` (the approved fingerprints, from the application only: the trust gate below), `empreinte_code`, `code_modeles` (a project's R code, to read before running it), `resume_modele`'s `code_r` (fingerprint, approved) and `etat`'s `code_interdit`; `retablir` (Redo, 1.1: `etat$retablissements`, the states Undo left, 20 at most, emptied by any new change in `memoriser`; Undo and Redo share `revenir_a` and `entree_inverse`, a merge's documents, figures and file state and a rename's document references included; a model fitted since stays and one changed since keeps its definition (`modeles_venus`: `definitions_changees(id, noms)`, called when a definition is fitted again with other settings, its note or kept settings change, notes the names in every undo entry, `changees`; that definition takes the place of the old one, by name, or by number for one renamed by its edit, unless it reads what the undo takes away; their terms, condition and settings follow the variables' names, `suivre_noms_variables`); both answer `documents`, the documents whose text they changed, which the windows read again); `renommer_variable`, `supprimer_variable`, `type_variable` (atelier.R, each one undo step and a data step, with `apercu`); `faire_demande` (Stop: see "Stopping a computation"); `paquet`: the reproducibility package, paquet.R, with the models the interface fitted, those it couldn't, `non_ajustes`, its documents as JSON text, the dialog's answers kept in the project, `doi` the package's own when Zenodo reserved one for its draft, `qr` the QR code of its link, written at `chemin` or in the session's folder; `paquet_ouvrir`: a package opened again, paquet.R's `deballer_paquet`, unzipped into a folder of the session, its files checked against its manifest, its project opened as a new project without a file, named after the package's folder, keeping where it came from in `p$depuis_paquet` (its title, DOI, `.zip` and the manifest's verdict: `resume_projet`'s `depuis_paquet`, never saved, nouveau.R's `enregistrer_projet`), its data's source the unzipped CSV by its path, and the results it deposited given back with what computes here, `ici`, and the packages in another version; `ouvrir` answers `paquet_ouvrir` for such a `.zip`, opening nothing, and `repondre_erreur` adds `pas_un_paquet` to the refusal of an archive that isn't one) |

## R code in projects: the trust gate

Opening a file never runs code from it (`docs/deploiement.md`). An R-code model's code (`moteur/R/code.R`) runs only when
its fingerprint, the SHA-256 the engine computes (`empreinte_code`), is among those this user approved on this computer:
code typed in New model and fitted, or read and run from the bar over a project. `main.js` keeps them in the settings
(`reglages.codeApprouve`, the latest 10,000) and gives the whole list to the engine at each start, before the window opens,
after a restart of the engine and after each approval (IPC `approuver-code`, `preload.js`: `bureau.approuverCode`), by the
request `code_approuve` with a secret drawn at each start and given to R alone (`NUEE_CODE_SECRET`, unset by `serveur.R`
once read): the windows have the token, not the secret, and the engine refuses their `code_approuve`. The engine checks the
fingerprint itself before anything runs the code (`exiger_code_permis` in `ajuster_code` and `ecrire_script_code`), so
every path that fits models (opening a project and its session, Update the data, a merge, an old version, What changed,
Export to R, a reproducible document) refuses unapproved code whatever the interface asks: `code_non_approuve`, with the
fingerprint, in the error's answer. An engine started by hand (a browser) has no secret: the interface gives it the
approvals, for its session. The policy `DisableCustomCode` (DWORD 1, or `NUEE_SANS_CODE=1` in the environment) gives R
`NUEE_SANS_CODE`: `definir_code`, `ajuster_code` and `empreinte_code` refuse, `etat` says `code_interdit`, and New model
doesn't offer the type. Plugins use the same machinery: see [Plugins](#plugins).

## Plugins

A plugin (`moteur/R/greffons.R`, 1.1) is a folder: its manifest, `plugin.json`, and its R files;
shared as a `.nueeplugin`, a zip of that folder (`plugin.json` at its root or in one folder). The
user guide's *Writing a plugin* page is the manifest's reference; `exemple/plugins` holds two
(occupancy, Mann–Kendall), which `node docs/site/construire.js` packages into `docs/site/greffons`
with the interface's own zip writer (`app/interface/zip.js`, a fixed date: the same bytes at each
build) for the documentation's downloads; `verifier_greffons.R` checks those are the repository's.

- **Where they are:** this user's in `<userData>/greffons`, one folder per plugin, given to the
  engine as `NUEE_GREFFONS` (main.js, `demarrerR`), where `greffon_installer` writes them (into a
  hidden folder first, then renamed over the old one); the organisation's in the folder of the
  `REG_SZ` policy `PluginsFolder` (or `NUEE_GREFFONS_ORGANISATION`, which an installed copy on Windows ignores), read only, as
  `NUEE_GREFFONS_ORGANISATION`. main.js also gives `NUEE_VERSION`, the version a manifest's
  `nuee` is compared with.
- **The fingerprint:** the SHA-256 (code.R's `empreinte_code`, `sha256_r` on an R without
  `tools::sha256sum`) of the canonical text `nuee plugin 1\n` then, for each file sorted by its
  path byte by byte (the manifest and the R files it lists), its path, the length of its text in
  bytes and its text, each followed by `\n`, texts in UTF-8 with LF line ends. Installing approves
  it through main.js as R code is approved (`approuver-code`, then `code_approuve` with the
  secret); the organisation's plugins need no approval (`greffon_permis`), and with
  `DisableCustomCode` they are the only ones (`definir_plugin`, `exiger_greffon_permis`). The gate
  is checked by `ajuster_plugin`, `predire_plugin` and `ecrire_script_plugin`, so that every path
  that fits a model refuses an unapproved plugin (`greffon_non_approuve`, with the fingerprint, id
  and version, in the error's answer: serveur.R's `refus_greffon` branch).
- **A model:** type `PLUGIN`, its plugin kept whole in `d$options$greffon` (`id`, `version`,
  `empreinte`, `fichiers`: the manifest's text and each R file's), its inputs in
  `d$options$entrees` (variable numbers by input id), its options in `d$options$options`, the
  columns it names in `d$options$colonnes`. The project carries it; opening one never runs it, and
  `resume_modele` says whether it may run here and which version is installed, which the bar uses.
  The model's own copy is what refits it; `greffon_mettre_a_jour` redefines a project's models with
  the installed version (one undo step). A fitted model is an R-code model's (`modele_valeur_code`)
  with the plugin's card, its inputs' variable names and its options' values.
- **Packages:** a manifest's `packages`, checked with `system.file` (the user library created
  since the engine started added to `.libPaths()` first), installed on request into the user
  library of the R in use (main.js `r-installer-greffon`, `r-installes.js`'s `installer` with
  `autres`).

## Running from the sources

## Stopping a computation

The engine is one R process serving httpuv on its single thread: while it computes, it reads no
request, so a "stop" request would wait for the end of what it should stop. Stop goes out of band
instead. `main.js` gives R the path of a stop file in this run's R temporary folder (`temporaireR`,
`NUEE_ARRET=<temporaireR>/arreter`; the file removed before R starts), and writes it when the
interface asks (IPC `arreter-calcul`, `preload.js`: `bureau.arreterCalcul`). `serveur.R` keeps the
path in `options(nuee.arret)` and removes the file at the start of every request, so a Stop that
came when nothing was computing stops nothing. The engine's long loops call `verifier_arret()`
(`moteur/R/arret.R`) at the start of each round: at most five `file.exists()` a second
(`proc.time()` in between), then `invokeRestart("arreter_calcul")`. Each request runs in
`faire_demande(f, q)`, which establishes that restart with `withRestarts` after a shallow copy of
`etat` (`mget`: the projects, the models, the undo and redo stacks…, not copied until changed):
stopped, it puts `etat` back as it was (the R console's log aside) and the request answers 400
`{ erreur, arrete: true }`, logged as a stop. A restart, not an error condition, so that no
`tryCatch(error = …)` around a round (a forest that fails for one CV group, an AIC candidate that
doesn't fit) takes it for a failed round and carries on; `on.exit` and `finally` still run (the RNG
state that `avec_graine` gives back). Without that restart (the engine loaded into R alone),
`verifier_arret()` raises an error of class `calcul_arrete`, which the request handler also turns
into `arrete`.

The loops that check: permutations (`permutations` of a PLS, `permanova_noyau`, `dispersion_noyau`,
`mantel_noyau`, `correlogramme_noyau`, `test_indval`, `stats_permutees` for an RDA's tests,
`ajustement_environnement` for the variables fitted to an ordination's axes, `moran`); the AIC
selection's candidates (`selection_aic`: `evaluer`); an NMDS's random starts (`nmds_noyau`); the power
simulations (`simuler_puissance`); the cross-validation rounds (`composante_validation`,
`validation_par_composante`, `tours_x_validation`, `validation_opls`, `validation_lineaire`,
`validation_mgcv`, `validation_gamm`, `validation_arbre`, `validation_foret`, `validation_boost`);
boosting, one tree at a time (`boosting`); a tree's stability draws (`stabilite_arbre`); TRIM's
stepwise selection (`pas_a_pas_trim`); iPLS's intervals; One model per response
(`modeles_par_reponse`); k-means' choice of k (`choix_k`); the steps replayed by Update the data
(`rejouer_etapes`). What can't stop before it ends: one fit in compiled code (nlme, lme4, glmmTMB,
mgcv, ranger's trees, distance sampling's and TRIM's estimation), the R console's and an R-code
model's code (the user's), Export to R's run of the script it writes, reading a file. Export to R
writes the engine's functions without these calls (`sans_arret`, from `texte_moteur` and
`dependances_moteur` in script_moteur.R and `code_definition_moteur` in communautes_script.R): the
script stops in R by Esc.

The interface (`api.js`) keeps the requests the user waits for (not the background ones,
`silencieux`) with when each began, and tells the page (`requetes`); after 1.5 s `app.js` shows
Stop (`majArret`) in an element of its own beside `#appli`, over the status bar after the engine's
state, `aria-live` so that a dialog's `majInert` leaves it usable (New model fits with its dialog
open), and above the dialog's shade (z-index 950). After 8 s without an answer it says the
computation only stops at its end. `occupe()` says "Computation stopped: nothing changed" rather than
an error; a session restored (`restaurerSession`), Update the data's fits (`etapes.js`:
`reajusterTout`, whose own Stop now writes the file too) and the refits after a rename stop their
loop at a stopped answer. `moteur/tests/verifier_arret.R` stops each of these loops through the
server's requests and checks the session unchanged; `essai_api.js` stops 999 permutations on the
real server and checks the next request removes the file.

Since 1.2 the long requests run in a second R (below), where the same file mechanism stops them
between two rounds, and a computation that doesn't look at it is killed: Stop then always works.

## Computing in the background

The engine was one R answering the window's requests one at a time: during a long computation
(a fit, 999 permutations, a power simulation) nothing else reached it, so the window could neither
show another model's view nor draw a plot, and Stop could only wait for a round's end. Since 1.2
the server (`serveur.R`) starts a second R at its start, the computing R (`moteur/calculateur.R`,
`arriere_plan_lancer` in `moteur/arriere_plan.R`): the same Rscript (`R.home("bin")`: on Windows
`bin/x64`, R itself) with the server's options (`main.js`: `NUEE_R_OPTIONS`, `--no-init-file` for an
installed copy), loading the engine as the checks do (each expression of `serveur.R` up to `appli`),
in a folder of its own inside the server's temporary folder.

- **What goes there.** The requests listed in `CALCULS` (the fits — `ajuster`, `reajuster`,
  `modeles_classe`, `par_reponse` —, predictions, permutations, the AIC selection, the power
  simulation, adjusted means and effects, an RDA's tests, k-means' choice, iPLS, What changed's
  rerun, the data's tests and rarefaction, Moran's I, Update the data, removing a step…) that concern a project
  (`projet_concerne`: `q$projet`, or the project of `q$modele`). `appli$call` asks
  `arriere_plan_demande` first; it answers a promise (`promises::promise`, which httpuv waits for)
  or `NULL`, the request then running here as before.
- **A task.** `arriere_plan_envoyer` writes `tache-<n>.rds` (written then renamed): the request
  (name, JSON body, language, the X-Nuee-Code header), the project and its models and predictions
  only when they changed since what the computing R has (`ARRIERE_PLAN$vu`: references, compared
  with `identical()`, which stops at a shared pointer), the projects and models gone since, the
  project's revision, its undo and redo stacks as stubs (`talons`: the labels `resume_projet`
  shows, without the project states), the id counter, and the approved fingerprints (R code and
  plugins, `APPROBATIONS_CODE`). The computing R (`faire_tache`) applies it to its own `etat`, runs
  `traiter_demande` exactly as the server would (the same JSON answer, character for character),
  and writes `resultat-<n>.rds`: the answer and what the request changed (`changements_tache`):
  projects, models and predictions changed or removed, the revision's increase, the undo entries
  it pushed (the project as received written as `PROJET_ENVOYE`, the server putting back its own),
  the names its stubs noted as changed definitions (`changees`, which the server's entries note too),
  whether it emptied Redo, the paired tests' pairs, the counter, its log entries, the namespaces it
  has loaded, and `autres`, anything else, logged and not taken.
- **Back in the session.** `arriere_plan_suivre`, a `later` callback run fifty times a second while
  there is work (httpuv's `service()` runs later's loop), reads the answer, checks that what the
  task changed is still here as it found it (else the task runs again on today's session, twice in
  the computing R, then here), reports it (`arriere_plan_reporter`), loads the namespaces the
  server lacks (so a ranger forest fitted there predicts here), and resolves the promise.
- **Waiting.** While a project computes, a request that could change it waits, in the order they
  came, until the computation is reported; `LECTURES`, the requests that change nothing in the
  session (`verifier_arriere_plan.R` checks statically that none can write in it), run at once and
  see the project as it was before the computation; other projects stay free. One task at a time:
  a second computation waits for the first.
- **Ids.** A task gets `RESERVE_IDS` (1000) numbers of its own (`nouvel_id`): the server, which may
  give some meanwhile (a file opened), takes the following ones; when it gave none, the counter
  goes back to the task's, so the ids are those a single R would give.
- **Stop.** `arriere_plan_arret` (each callback, and at the top of `appli$call` before the request
  removes main.js's file) answers the computations not begun "stopped" at once, writes the computing
  R's own stop file, and after `ARRET_PATIENCE` (1.5 s) without an answer kills it
  (`tuer_processus`: `pskill` with SIGKILL, SIGTERM on Windows where SIGKILL is `NA` and
  `TerminateProcess` is SIGTERM) and starts another, the session given to it again.
- **Gone.** Every two seconds of a task, the server connects to the port of an httpuv the computing
  R opened (`port_ouvert`: httpuv's thread accepts even while R computes). Gone without having read
  its task, the task goes to a new computing R; gone during it (out of memory?), the request fails,
  nothing changed. The computing R stops by itself when the server's port stops answering.
- **Without it** (`NUEE_SANS_ARRIERE_PLAN=1`, no Rscript, not ready after two minutes, the browser
  version, the engine's checks), everything runs here as before.

The window: `body.occupe` no longer turns every pointer into a progress one (the status bar says
the computation); New model's dialog (`dialogues.js`) sets itself aside (`ui.js`'s
`dialogue().cacher()`) when the fit takes more than 1.5 s, the window being free meanwhile, and
comes back with its settings and the error if the fit fails.

Where a computation is. The long loops give their round and their number of rounds to
`verifier_arret(fait, total, quoi)` (`arret.R`; `quoi` a word the interface translates:
validation, preparation, composantes, permutations, simulations, departs, arbres, tirages,
intervalles, k, reponses, etapes; the AIC selection's candidates and TRIM's stepwise rounds have no
known number and give none). `noter_progres` keeps the levels, outermost first: a loop inside
another is known by its depth in the call stack (`sys.nframe`), and a round of a loop forgets the
deeper ones that ended before it. In the computing R, `options(nuee.progression)` is a file of its
folder, written at most four times a second with the task's number; the request `progression`
(`arriere_plan_progression`, a `LECTURE`) gives the task's request, its seconds, its fraction
(`fraction_progres`: the round under way of each level counts for what the level inside it has
done) and its levels, and the requests waiting. `sans_arret` takes the calls out of Export to R's
scripts with or without arguments (a recursive PCRE pattern). The interface: `progression.js`.
In the browser version, whose one R can't be asked while it computes, `options(nuee.progression)`
is a function (`navigateur.R`: `progres_navigateur`) that sends the same levels, with the request's
number, name and seconds, at most four times a second through `webr::eval_js` on a BroadcastChannel
of the tab (`nuee-progres-<tab>`); `progres_tache`, called by `moteur_webr.js` before each request,
says which request R begins. `progression.js` makes from them the answer `progression` gives, the
requests the user waits for besides being those waiting; a request ended (`finTache`) says nothing
more. A permutation test shared among the page's R: the piece of the page's R says its outermost
loop on the whole (`PROGRES$echelle`, the whole over its piece).

- `Lancer Nuee.cmd`: the launcher.
- `LISEZ-MOI.txt` and `USER-GUIDE.txt`: the user guide, in French and in English (both are also
  in `application/resources/`, where *Help › User guide* (F1) shows the one in the interface's
  language in a panel, through the engine's `guide` request, and opens it as a text file).

Electron crashes when started from a network share, so the launcher mirrors `application/` to
`%LOCALAPPDATA%\Nuee` with robocopy and starts it from there. The first launch copies everything;
later launches copy only what changed on the share. The launcher puts "Nuée" shortcuts on the
desktop and in the Start menu, and starts the app with `--lanceur-nas`: the app then lists that
copy in Settings › Apps (key `HKCU\…\Uninstall\Nuee`), with `resources\desinstaller.cmd` as its
uninstaller. No administrator rights are needed.

**`installateur/Nuee-Setup-<version>.exe`**, made from the same `application/` folder with
electron-builder (NSIS): install for the current user (no administrator rights) or for all
users, Start menu and desktop shortcuts, and an entry in Settings › Apps with its uninstaller.
It is not code-signed, so SmartScreen warns on first run. `SANS_INSTALLATEUR=1` skips it.
An installed copy asks `api.github.com/repos/4rtefakt/nuee/releases/latest` once per start
whether a newer version exists, and shows a link in the status bar (off in Help; never for the
network-share copy or when running from the sources). If the release has a
`Nuee-Setup-<version>.exe` asset with a SHA-256 `digest` (GitHub computes it on upload), the
link offers the one-click update (`app/main.js`): the installer is downloaded from
`github.com/4rtefakt/nuee/releases/download/` into `%TEMP%\nuee-mise-a-jour`, its SHA-256 must
match, unsaved projects are saved or left as the user says, R is stopped, and a `cmd.exe`
without a console waits two seconds (by running `Nuee.exe` as Node: `ping`, a console program,
opened a black window up to 0.9.5), runs the installer silently (`/S`, `/currentuser`, or
`/allusers` when Nuée is installed for all users, which Windows asks to allow: its entry in
Settings › Apps is under HKLM, else Program Files decides, `app/installation.js`; `/D=` the
current folder), then starts Nuée again with the same `--user-data-dir`. That `cmd.exe` is
started by a go-between that ends at once (`Nuee.exe` with `ELECTRON_RUN_AS_NODE`), so it isn't
in Nuée's process tree: the installer closes `Nuee.exe` with everything it started, and in one
test out of three it killed a `cmd.exe` started directly by Nuée, before installing anything.
The installer removes the old version first (keeping the settings) and keeps each file's
original date; the next start deletes the downloaded installer. The new version then shows its
own interface: the engine serves it with `Cache-Control: no-cache` (a `304` when nothing
changed), and the first start of a new version empties Chromium's HTTP cache (`reglages.json`
keeps the version). Up to 0.9.5 the interface came without `Cache-Control`, Chromium kept it
fresh for a tenth of its age, and right after an update the new version showed the old
interface.

To test it without a release, set `NUEE_SOURCE_MAJ` to an address answering like the GitHub
API (a `tag_name` above the installed version and an asset with `name`, `size`,
`browser_download_url` and `digest`); the installer may then come from anywhere. Checked
end to end: install the build, offer a "0.9.9" whose installer is that same build
from a local server, first with a wrong SHA-256 (refused, nothing installed), then the right
one (downloaded, installed, restarted with the same profile), and uninstall it.

Settings live in `%APPDATA%\Nuee` (`~/Library/Application Support/Nuee` on macOS,
`~/.config/Nuee` on Linux); `--user-data-dir=<folder>` uses another one (a clean profile for
tests or screenshots).

### On macOS

R is brought along, as on Windows: CRAN's R 4.6.2, from its `.pkg` (`sonoma-arm64` for Apple
silicon, `big-sur-x86_64` for Intel), with the engine's packages installed in R's own library,
which the build copies like the Windows one:

```bash
sudo installer -pkg R-4.6.2-arm64.pkg -target /
sudo Rscript -e "install.packages(c('jsonlite', 'httpuv', 'openxlsx', 'haven', 'readxl', 'RSQLite', 'ranger'), lib = .Library, repos = 'https://cloud.r-project.org')"
PYTHON=<a python3 with PyInstaller> node app/construire.js <output folder> [R folder]
```

The R folder is `/Library/Frameworks/R.framework/Resources` unless given. Without administrator
rights, R can be expanded from its `.pkg` instead (`pkgutil --expand-full R-4.6.2-arm64.pkg R`),
made to run from there with `node app/r-macos.js R/R-fw.pkg/Payload/R.framework/Versions/4.6/Resources`
(after removing its `library/tcltk`, which loads CRAN's separate Tcl/Tk), and given to the build;
run `r-macos.js` again after installing the packages with that R (`RHOME=<R folder>
<R folder>/bin/Rscript -e "install.packages(…)"`).

CRAN builds R to sit in `/Library/Frameworks/R.framework`: its programs and libraries, and the
packages built for it, name the libraries they load by their path there, and `bin/R` names its
own folder there. `app/r-macos.js` makes the copy in `Nuée.app/Contents/Resources/R` run from
wherever the application is: each such name becomes `@loader_path/…` (`install_name_tool`), and
each file changed is signed again ad hoc, since an Apple silicon Mac runs nothing whose signature
no longer matches; `bin/R` finds its folder from its own path. The libraries keep their own names
(`/Library/…/libR.dylib`), so that a package the researcher installs from the R console, built
for CRAN's R, gets the `libR` already loaded. A library loaded from anywhere else than R, the
system or XQuartz (`/opt/X11`, which only the X11 and cairo devices load, as with CRAN's R) stops
the build: it would be missing on another Mac. `Rscript` itself still names
`/Library/Frameworks` for R's folder: `main.js` starts it with `RHOME` set to the application's
R (and `R_LIBS`, as on Windows), and so does Quarto when it runs a reproducible document's R
chunks with the engine's R (`QUARTO_R`). `app/tests/essai_r_macos.js` checks the names and the
`bin/R` change.

The build produces:

- **`Nuee/`**: `Nuée.app` (Electron in French and English, R without its manuals, tests, debug
  symbols or Tcl/Tk, the engine, the example project, the converter compiled with PyInstaller as
  on Windows, `outils/export_project`) and the user guide. The whole application is then signed
  ad hoc (`codesign --deep`) and checked: there is no Apple Developer ID, so it isn't notarized,
  and macOS asks once to allow a copy downloaded with a browser (*System Settings › Privacy &
  Security › Open Anyway*). Signing it with a Developer ID for notarization would need the
  hardened runtime, and an entitlement letting R load packages not signed by the same team
  (`com.apple.security.cs.disable-library-validation`), for those installed from the console.
  `Info.plist` declares `.nuee` projects and, on Apple silicon, macOS 14 at least (CRAN's
  packages for R 4.6 need it; Electron 45 needs 13).
- **`installateur/Nuee-<version>-<arch>.dmg`**: `Nuée.app` beside a link to Applications
  (electron-builder; `SANS_INSTALLATEUR=1` skips it).

`main.js` keeps a menu bar on macOS (*Nuée*, *Edit*, *Window*, in the interface's language):
without its Edit menu, ⌘C, ⌘V, ⌘X, ⌘A and ⌘Z would do nothing in text fields; the interface
takes those keys elsewhere, and the menu only gets the keys the page didn't use. *Quit* asks
about unsaved projects as *File › Quit* does. A `.nuee` double-clicked in the Finder comes as an
`open-file` event, not on the command line. The temporary folders are each user's own
(`$TMPDIR`).

### On Linux

R is not brought along: a Linux R build is tied to its distribution's libraries (BLAS, ICU,
readline…), so the application uses the system's R, found on the `PATH`, then in
`/usr/local/bin`, `/usr/bin` and `/opt/R/<version>/bin` (`RSCRIPT=<Rscript>` picks another, for
the build too; in the application, *File › Settings…* another, `/opt/R`'s listed). If R or one of
the engine's packages is missing, the error at start-up says what to install. The `.usp` converter needs only Python's standard library: it is shipped as
`resources/convertisseur/*.py` and run with `python3` (`PYTHON=<python>` picks another).
`moteur/serveur.R` switches R to `C.UTF-8` when it starts without a UTF-8 locale (a launch
from the desktop menu with no `LANG`), since the engine's files are in UTF-8.

The build produces:

- **`Nuee/`**: the application (`./nuee` starts it) with the engine, the example project, the
  converter and `LISEZ-MOI.txt`, readable by every user (the packager builds in a folder made
  by `mkdtemp`, mode 700, which the `.deb` would otherwise install as `/opt/Nuée` for root
  alone).
- **`installateur/`**, made from that folder with electron-builder:
  - `Nuee-<version>-amd64.deb`, which depends on electron-builder's list plus `libgbm1` and
    `libasound2` (Electron loads them; a minimal Ubuntu 22.04 lacks `libgbm1`), then on
    `r-base-core` and `r-cran-httpuv`, `r-cran-jsonlite`, `r-cran-openxlsx`, `r-cran-haven`,
    `r-cran-readxl`, `r-cran-foreign`, `r-cran-nlme`, `r-cran-mgcv`, `r-cran-mass`,
    `r-cran-rpart`, `r-cran-cluster` (Debian keeps R's recommended packages, these six among
    them, out of `r-base-core`), `r-cran-ranger`, and recommends `python3` and `r-recommended` (for the R
    console, as on Windows). It installs into `/opt/Nuée`, adds `nuee.desktop` to the
    applications menu and, on Ubuntu 24.04 and later, the AppArmor profile Electron's sandbox
    needs;
  - `Nuee-<version>-x86_64.AppImage` and `Nuee-<version>-x64.tar.gz`, for other distributions,
    with R and the packages installed apart. The AppImage uses electron-builder's default
    runtime, which mounts it with FUSE 2 (`libfuse2`). Ubuntu 24.04 and later keep
    unprivileged user namespaces to programs with an AppArmor profile, so an AppImage there
    starts only with `--no-sandbox`.

  `SANS_INSTALLATEUR=1` skips them. Building the `.deb` needs `fpm`, which electron-builder
  downloads; on NixOS, where its `#!/bin/bash` doesn't run, set `USE_SYSTEM_FPM=true` with
  `fpm` installed.

`package.json` names the desktop file (`desktopName`), so the windows' app id (`nuee`) matches
the menu entry and docks group them under its icon. The tests run the same way:
`node tests/essai_api.js` and `Rscript moteur/tests/verifier_*.R` find `Rscript` on the `PATH`.

## Workflows, end to end

`app/tests/essai_appli.js` checks briefly that a built program starts, computes and quits.
`app/tests/essai_parcours.js` goes through the workflows people actually do, in a built program,
through its window: real clicks and keys on its menus, dialogs, plots and document editor, sent
over the Chrome DevTools Protocol, then what the window shows checked against what the engine
answers. It starts the program once with a temporary profile, runs the scenarios of
`app/tests/parcours/` in their numbers' order, and between two of them closes the projects and
loads the window again. It needs Node 22 or later and nothing from npm.

```bash
cd app

xvfb-run -a node tests/essai_parcours.js '/opt/Nuée/nuee'            # Linux, on a server (in a container as root, add --no-sandbox)
node copier-vendor.js && node tests/essai_parcours.js node_modules/electron/dist/electron.exe <screenshots> .  # from the sources, no build
NUEE_HORS_ECRAN=1 node tests/essai_parcours.js <program> <screenshots> --disable-features=CalculateNativeWinOcclusion  # on a desktop someone uses: no window on the screens
```

It never waits a fixed time: each step waits for what it needs (an element, a request's answer, a
status message), up to a minute for each (`NUEE_ATTENTE`, in milliseconds; fits up to three), so a
slow computer only makes it longer; `NUEE_TRACE=1` prints the waits that took over a second. The
window's page is laid out at 1400 × 900 whatever the screen (GitHub's Windows machines have
1024 × 768). The whole run takes about 45 seconds on a recent Windows PC, longer with several
runs at once. The program's main process is reached through its Node inspector (`--inspect`): there
the system's file dialogs get the answers a scenario queued (`n.fichierAOuvrir`,
`n.fichierAEnregistrer`; one asked for without an answer is cancelled, and fails the scenario), a
question (unsaved projects) the answer queued, and opening a file (`shell.openPath`), following a
link or adding a recent document is only recorded: a run never opens Word or a browser, nor
touches the system's list of recent files. With `NUEE_HORS_ECRAN=1` (a run on a computer someone is using) the
windows stay off the screen and out of the taskbar, never take the focus, and are still drawn
(Chromium's occlusion tracking and background throttling off). The check for a newer version asks a closed local port
instead of GitHub (`NUEE_SOURCE_MAJ`). Each scenario also fails on an error in the page, a request
the engine refused, a security policy violation or an unexpected `confirm()` (answered Cancel at
once). A program that stops or stops answering is started again for the next scenario. With
`NUEE_HORS_ECRAN=1` (a run on a desktop someone is using), the main process keeps every window
beyond the screens' left edge, shown without the focus, out of the taskbar, never raised, still
drawn (`--disable-features=CalculateNativeWinOcclusion` for the program, background throttling off),
and the profile gets a free port of its own (`reglages.json`): never the installed Nuée's usual one.

A new scenario is a file `app/tests/parcours/<number>_<name>.js` that exports
`executer(n, verifier, contexte)`. `n` drives the window: `app/tests/parcours/pilote.js` says what

## Signing in to GitHub and GitLab

Nuée signs in with the OAuth 2.0 device flow (`app/comptes.js`): it shows a short code, the
person types it on the site's page and approves Nuée, and Nuée receives a token. It needs one
OAuth application per site, registered once, whose public client id goes in `app/comptes_ids.js`.
No client secret is used: never put one in Nuée. Until an id is filled in, signing in to that
site says it isn't set up, and a token can still be given.

- **GitHub**: an OAuth App (not a GitHub App), registered by the account that owns the repository
  (its Settings › Developer settings › OAuth Apps › New OAuth App). Application name `Nuée`,
  homepage `https://nuee.io`, authorization callback URL `http://127.0.0.1/` (the form requires
  one; the device flow never uses it). Then, in the app's settings, tick *Enable Device Flow*. No
  scope is chosen at registration: Nuée asks for `repo` (private repositories and their
  collaborators). Its tokens don't expire (if the app is made to expire them, Nuée renews them
  with their refresh token). The *Client ID* (`Ov23li…`) goes in `comptes_ids.js` under
  `'github.com'`; no client secret needs to be generated.
- **gitlab.com**: an application owned by a group (the group's Settings › Applications › Add new
  application) or by a user (Edit profile › Applications). Name `Nuée`, redirect URI
  `http://127.0.0.1/` (required by the form, unused by the device flow), *Confidential* unticked,
  *Device authorization grant* ticked (a new application has it off, and GitLab then answers
  `access_denied`), scopes `api` (creating a project, adding a member), `read_user` (the account)
  and `write_repository` (sending versions). The *Application ID* (64 hexadecimal digits) goes in
  `comptes_ids.js` under `'gitlab.com'`; the *Secret* it shows is not used. Its tokens last two
  hours; Nuée renews them with their refresh token.
- **A self-hosted GitLab** (17.3 or later; 17.2 behind the `oauth2_device_grant_flow` flag): its
  administrator registers Nuée the same way, as an instance-wide application (Admin › Applications ›
  New application; *Trusted* skips the approval page), and gives its *Application ID* to the
  people who use Nuée. They type it once in the sign-in dialog, which keeps it in their settings
  (`reglages.json`, `comptes.serveurs`). An older GitLab answers 404: Nuée says so and offers a
  token.

`node tests/essai_comptes.js` checks all of it against a local stand-in of both sites; nothing in
the checks reaches github.com or gitlab.com.

## Signing in to Zenodo

The deposit on Zenodo (`app/zenodo.js`) signs in with OAuth 2.0's authorization code: Nuée
listens on `127.0.0.1`, opens Zenodo's page in the browser, where the person signs in and
authorizes Nuée, and Zenodo sends the browser back to Nuée with a code, which Nuée exchanges for a
token, kept as a pasted one is. It asks for `deposit:write` alone (Zenodo's page says "Allow
upload (but not publishing)"); Nuée never publishes. Zenodo's tokens last 60 days (zenodo-rdm's
`OAUTH2_PROVIDER_TOKEN_EXPIRES_IN`) and aren't renewed: invenio-oauth2server renews only
confidential clients' tokens, and keeps one token per application and account, so a new sign-in,
on this computer or another, replaces the one before; Zenodo then refuses that one (401), which
Nuée forgets, offering to sign in again. Zenodo's `/oauth/token` sends no CORS headers: a page
couldn't exchange a code (the browser version doesn't deposit).

Each server needs one OAuth application, registered once, whose public client id goes in `IDS`
at the top of `app/zenodo.js`; Clément registered both (2026-11-18). No client secret is used:
never put one in Nuée. A copy built with a placeholder instead of an id offers the personal access
token alone in the deposit dialog.

- **zenodo.org**: signed in with the account that will own the application, Account ›
  Applications › Developer applications › New application
  (`https://zenodo.org/account/settings/applications/clients/new/`):
  - Name: `Nuée`
  - Description: `Deposits reproducibility packages made with Nuée as drafts, their DOI
    reserved. Nuée never publishes.`
  - Website URL: `https://nuee.io`
  - Redirect URIs, one per line, exactly as written (Zenodo sends the browser back only to these
    addresses, character for character; Nuée takes the second port when another program has the
    first: `PORTS_RETOUR`):

        http://127.0.0.1:47864/zenodo
        http://127.0.0.1:47865/zenodo

  - Client type: *Public* (Nuée can't keep a secret: its code is open and it runs on the user's
    computer).

  No scope is chosen there: Nuée asks for `deposit:write` when it signs in. Once saved, the page
  shows the *Client ID* (40 letters and digits), which goes in `IDS` under `'zenodo.org'`, and a
  *Client Secret*, which Nuée doesn't use: leave it there.
- **sandbox.zenodo.org**: the same, with a sandbox account (it has accounts of its own:
  `https://sandbox.zenodo.org/account/settings/applications/clients/new/`), its *Client ID* under
  `'sandbox.zenodo.org'`.

`node tests/essai_zenodo.js` checks it against a local stand-in for Zenodo's OAuth server, and
journey `15_paquet` signs in through the deposit dialog against one; nothing in the checks reaches
zenodo.org.

## Browser version

The same interface and engine run in a browser tab, R included, through webR 0.6.1 (R 4.6.0
compiled to WebAssembly): nothing to install, and the data stay in the tab.

**Build and serve.**
- `node app/construire_navigateur.js [<folder>] [<webR folder>]` builds a static site, in
  `dist/navigateur` unless given (62 MB):
  - the interface, its page saying `window.NUEE_MOTEUR = 'webr'` (`navigateur.js`), its security
    policy with `'wasm-unsafe-eval'` (R's WebAssembly) and `https://repo.r-wasm.org` (R's packages);
  - the engine's files (`moteur/` without its tests, `exemple/`, the user guide that the help panel
    asks the engine for, `app/package.json` where the protocol request reads Nuée's version),
    listed in `moteur-fichiers.json`;
  - webR, from the npm package `webr` (a devDependency, pinned: the engine's packages are built
    for its R): its browser build `webr.js`, served as `webr/webr.mjs` (npm's own `webr.mjs`
    imports Node's modules), `webr-worker.js`, `R.js`, `R.wasm`, BLAS, LAPACK and base R in
    `vfs/`; or the files of a folder like `webr.r-wasm.org/v<version>/`;
  - `_headers`, the two headers below, for hosts that read such a file.
- Any web server will do, if it sends `Cross-Origin-Opener-Policy: same-origin` and
  `Cross-Origin-Embedder-Policy: require-corp` (webR then shares memory with its worker).
  `node app/servir_navigateur.js [<folder>] [<port>]` serves it so on 127.0.0.1.
- `node app/miroir_webr.mjs [<folder>]` gives a built site its own copy of webR's repository,
  for a host that serves R's packages itself: the webR binaries of `PAQUETS_WEBR` and what they
  depend on (Depends and Imports, as `webr::install` follows them, less what webR's R has: 39
  packages, 38 MB, stringi's 14 MB the largest), for the R of the site's webR (4.6), in
  `repo/bin/emscripten/contrib/4.6/` with their own index (`PACKAGES`, `PACKAGES.gz` and
  `PACKAGES.rds`, R's own serialization of the matrix `read.dcf` gives: R reads the `.rds` first).
  Each binary is downloaded once from repo.r-wasm.org into `app/node_modules/.cache/nuee-webr/miroir/4.6`
  and checked against its index, read again at each build (the version its name says, its MD5).
  The site's `navigateur.js` then says `window.NUEE_MIROIR_WEBR = 'repo/'`.
- It is served at **https://nuee.io/app/**: `vitrine/construire.mjs` builds it into
  `vitrine/dist/app` with these two scripts, the landing page's `_headers` gives `/app/*` the two
  headers above and takes the landing page's security policy off it (the app's page has its own),
  and `/app` redirects to `/app/` (see `vitrine/README.md`). Without a copy of webR's repository,
  as `servir_navigateur.js` serves a site by default, R's packages come from repo.r-wasm.org.
  nuee.io's French page links to `/app/?langue=fr`: when the browser keeps no language yet, the
  address's (`fr` or `en`) is the interface's and is kept as View › Language keeps it, so that a
  choice made since wins over it (`i18n.js`).

**The engine in the page.**
- `api.js` sends each request to `moteur_webr.js` instead of the local server. That module starts
  webR, writes the engine's files into its file system, installs R's packages (below), and reads
  `moteur/serveur.R` up to its HTTP server (`appli <- list(`), as the engine's checks of the
  requests read it (`verifier_etapes.R`): every request goes to
  `traiter_demande()`, which the HTTP server calls too, with 1.1's handling (the approval secret,
  Stop's `faire_demande`, the refusals that say more than their message): the same code, the same
  numbers.
- The packages: `paquets_webr.js` (`PAQUETS_WEBR`): jsonlite, nlme, mgcv, MASS, rpart, cluster,
  foreign, openxlsx, readxl, haven and zip, with what they depend on (39 packages, 77 MB once
  installed, 35 MB of them stringi's, which openxlsx needs). Every package the engine loads is on
  repo.r-wasm.org for R 4.6, but two are left out (`SANS_WEBR`): RSQLite, whose webR build needs
  OpenSSL (`X509_free`), which webR doesn't have, and ranger, whose webR build loads, then stops at
  its first forest (`thread constructor failed: Not supported`: webR has no threads). A package
  whose library fails to load leaves webR unable to load any library after it (Emscripten keeps
  its missing symbol), so these are never installed. Each package is installed on its own: one
  that fails leaves only its features out (`?sans=a,b` leaves those out, to see it).
- Where they come from (`depotsPaquets`): from the site's own copy of webR's repository when
  `navigateur.js` declares one (`miroir_webr.mjs`, as on nuee.io), a package that copy has from
  it alone (`webR.installPackages([p], { repos: [copy] })`): a first visit then asks nothing of
  another site. Otherwise, and for what the copy lacks, from webR's repository, repo.r-wasm.org.
  With a copy, R gets `options(webr_pkg_repos = c(<copy>, "https://repo.r-wasm.org"))`, in that
  order, for the packages of R code and plugins below.
- R gets `options(nuee.navigateur = TRUE, nuee.paquets_absents = ..., nuee.paquets_sans_webr = ...)`.
  A request refused for a package the page lacks, by `loadNamespace()` or by the engine's own
  refusal that names it, says that it needs the desktop application (`navigateur.R`:
  `erreur_navigateur`, called by `repondre_erreur`; the engine's classed refusals keep their
  class): "Random forests: Nuée's desktop application is needed (the R package ranger isn't in
  the browser version)." So do `.usp` files (`convertir_usp`: their converter is a program, and
  the page starts none). The rest goes on.
- R code and plugins (1.1): the packages a model's code or a plugin names are installed from the
  repositories of `webr_pkg_repos` (the site's copy, then webR's repository: for an R-code
  model's own package such as Kendall, repo.r-wasm.org) before it runs, and any still missing
  when it runs, then it runs again
  (`navigateur.R`: `installer_paquets_navigateur`, from `evaluer_navigateur` in `ajuster_code` and
  `evaluer_greffon`, and `exiger_paquets_greffon`); never one whose dependencies include a package
  of `SANS_WEBR`. One the repository doesn't have, or webR can't load, says that the desktop
  application is needed (`paquets_absents_navigateur`), instead of `install.packages()`. File ›
  Plugins… installs a plugin in the page (a `.nueeplugin`, or a `plugin.json` with its R files,
  chosen there) into `NUEE_GREFFONS=/greffons` of webR's file system, kept in the browser's
  storage after each install or removal and put back at each visit (`moteur_webr.js`:
  `garderGreffons`, `rendreGreffons`; `secours_navigateur.js`: `magasin('nuee-greffons')`, OPFS
  else IndexedDB); its missing packages install from webR's repository (`vues_greffons.js`:
  `installerWebR`). The code and plugins approved in the page are kept by the browser
  (`localStorage['nuee-code-approuve']`, the latest 10,000, as `main.js` keeps them in the
  settings) and given to the engine at each visit (`approuver_codes`); `NUEE_VERSION` is the
  interface's version.
- Texts in the desktop's order: webR's R sorts texts by their bytes (no ICU, and musl's `strcoll`
  is `strcmp`), "B" before "a" and "traité" before "témoin", so a table opened in the page would
  get other categories first, and its regressions another reference. `trier_textes()`
  (`navigateur.R`) orders them with the browser's `Intl.Collator` in webR's worker
  (`webr::eval_js`), where the engine makes categories from texts (`nouveau.R`, `variables.R`,
  `etapes.R`, `kobo.R`, `formats.R`'s jamovi levels) and for the keys of a pairing (`ordre_cles`);
  elsewhere `sort()`, as before.
- Writing what webR's iconv can't (musl's: no `//TRANSLIT`, `*` for any letter outside ASCII):
  dBase texts in Windows-1252 and variable names in ASCII take the base letter of an accented
  one from a table of U+00C0 to U+024F (`formats.R`: `en_cp1252`, `en_ascii`, `sans_accents`);
  only when iconv doesn't transliterate itself, so the desktop's files stay the same.
- Files the user opens go into webR's file system (`deposer`; several in one folder,
  `deposerEnsemble`: a raster beside its `.tfw`); those the engine writes are downloaded
  (`telechargerFichier`) or read (`lireFichier`: a reproducible document's scripts, put in a
  `.zip`). Save writes the project at its place in the browser's storage (History, below), never
  where a project opened from a file was put, then downloads it. A linked BibTeX or CSL-JSON file
  has its references kept in the document, as pasted ones. Recent files aren't kept, and views
  don't move to windows of their own (another window would start an R of its own, without the
  projects).
- Each webR has one core. Other webR instances (the engine without the server or packages,
  `?aides=N`, by default one per core left, 4 at most) take pieces of the requests listed in
  `TRAVAUX` (`serveur.R`), so far the permutation test:
  - `travail_preparer()` draws the shuffles and writes the tasks to a file;
  - each instance runs `travail_morceau()` (`moteur/R/travaux.R`), computing the X side of the
    model once for its piece, as one R does (`cote_x_modele`), with 1.1's `verifier_arret()`
    before each refit;
  - `travail_finir()` assembles the pieces with the same functions as the request in one R.
  - The answer is the one-R answer: `identical()` to 1.0's loop, in one piece and in three.
- Stop (1.1): no file can reach R while it computes, so Stop interrupts it (`webR.interrupt()`,
  `moteur_webr.js`: `arreter`, and the other R of a shared request), which R sees within a
  thousand evaluations, anywhere in R code (not in a package's compiled code: a fit of nlme or mgcv
  ends first). A request is interrupted in its computation only, where the interruption becomes
  the restart `arreter_calcul` of the desktop's stop file (`navigateur.R`: `calcul_arretable`,
  from `faire_demande`): the request answers "stopped" and the session is as it was. An
  interruption from before it (Stop just as the last one ended) is passed first, and one that
  comes once the computation is done doesn't change its answer (`hors_interruptions`, around
  `traiter_demande`, `travail_preparer` and `travail_finir`; `passer_interruption`).

**What 1.1 has in the page.** Data steps and Update the data (the new file chosen in the page; a
project opened in the tab has its file there as its source, read again while the tab lives, not

accessibility, the documents (Quarto's `.qmd` in a `.zip`), R-code models and plugins as above,

and this computer's git sign-in (below), Zotero in the citations dialog, and Compile with Quarto
("in the desktop application"); File › Settings… (the installed R) and Quit aren't in the menu, as
in any browser; Help › Restart the R engine and the zoom are greyed out (reloading the page
restarts R, the browser zooms by itself); the native dialogs are the browser's file choosers.

**A reproducibility package's link (1.2).** `?doi=<doi>` or `?record=<id>` (the README of a
package deposited on Zenodo gives `https://nuee.io/app/?doi=<doi>`, and its QR code too) fetches the
package from Zenodo and shows its main document first, without R (lecture.js, above), then opens
it, or opens and reruns it, as File › Open a reproducibility package… does (relancer.js:
`paquetDuLien`, `ouvrirPaquetDuLien`; that command, File › Open on a package's `.zip` and a `.zip`
dropped work in the page too, the file chosen there). The page asks nothing of any other site: only Zenodo's API, which
answers any page (`Access-Control-Allow-Origin: *` on `/api/records/<id>`, its files and their
content, Range included), so the site's security policy adds `https://zenodo.org` to
`connect-src` (`construire_navigateur.js`).
- The record (`recordZenodo`): a version's DOI, `10.5281/zenodo.<id>`, is the record `<id>`
  (`GET /api/records/<id>`, its `doi` the DOI given); a concept DOI's id is its parent's, which
  Zenodo's records endpoint redirects to its latest version (invenio-rdm-records' `read`, on
  `NoResultFound`: `read_latest`, then a redirect to it, which `fetch` follows), its `conceptdoi`
  the DOI given; any other DOI (a record of Zenodo may carry one of its own), or a redirect that
  didn't reach the page, goes to the search, `GET /api/records?q=doi:"<doi>" OR conceptdoi:"<doi>"`
  with `allversions=true&sort=version` (zenodo-rdm maps the legacy fields `doi` and `conceptdoi` to
  the records' DOIs), the record of that DOI, else the latest version of that concept. The records
  endpoint answers from the database; the search from its index, a little after a publication.
  Its JSON is Zenodo's (`ZenodoJSONSerializer`, `application/json`): `id`, `doi`, `conceptdoi`,
  `metadata.title`, and `files`, an array of `{key, size, checksum, links}`.
- Its package: each `.zip` among its files, downloaded from
  `https://zenodo.org/api/records/<id>/files/<key>/content` (built from the record's id and the file's
  key, never an address the record gives), until one is a package, read in the page
  (`lirePaquetZip`, with zip.js's `lireZip`: the central directory, stored or deflated files that the
  browser's `DecompressionStream('deflate-raw')` inflates; a folder with a `.nuee` and
  `MANIFEST.sha256` at its top); one it can't read (ZIP64…) is left to the engine. Then its main
  document (lecture.js), and on Open the whole project or Rerun the models, the `.zip` in webR's

**nuee.io's relay (1.2), for sharing from the page.** A page can't use git's endpoints on GitHub and
GitLab, nor those of their device flow: they send no CORS headers (asked with an `Origin`,
github.com's answer 404 or 405 without any, gitlab.com's 200 without any; only gitlab.com's
`/oauth/token` sends `Access-Control-Allow-Origin: *`). Their APIs answer any page:
`api.github.com` and `gitlab.com/api/v4` send `Access-Control-Allow-Origin: *` on their preflights
(which allow `Authorization`, `Content-Type` and every method `comptes.js` uses) and on their
answers, 401 included, so the page asks them directly (its `connect-src` then names them). So do
the accounts' pictures on `avatars.githubusercontent.com` (with `Cross-Origin-Resource-Policy:
cross-origin`) and `secure.gravatar.com`, but not the ones uploaded to GitLab
(`gitlab.com/uploads/…`: neither CORS nor CORP, so the page can't show them). The rest goes
through nuee.io's Worker (`vitrine/src/relais.js`), in the form of isomorphic-git's `corsProxy`
(`corsProxy: 'https://nuee.io/relais'`): `https://nuee.io/relais/<host>/<path>` goes to
`https://<host>/<path>`, for these requests alone, anything else 404:
- github.com and gitlab.com, git's smart HTTP: `GET <repository>/info/refs?service=git-upload-pack`
  or `git-receive-pack`, `POST <repository>/git-upload-pack` or `git-receive-pack`; `<repository>`
  an owner and a name on GitHub, up to 20 groups and a name on GitLab, with or without `.git`;
- the device flow: github.com's `POST login/device/code` and `login/oauth/access_token`,
  gitlab.com's `POST oauth/authorize_device` and `oauth/token` (its tokens' renewal too).

How it answers:
- CORS for Nuée's pages alone: `https://nuee.io` and `https://www.nuee.io` (the same site, which
  doesn't redirect), and `http://127.0.0.1` and `http://localhost` on any port, for the checks; on
  nuee.io, the page asks it from its own origin. Another `Origin`, or none from another site's page
  (`Sec-Fetch-Site: cross-site` or `same-site`), gets 403 before anything is sent on. Preflights
  are answered by the relay (`GET, POST`; `Accept, Authorization, Content-Type, Git-Protocol`; two
  hours); the origin is given back in `Access-Control-Allow-Origin`, with `Vary: Origin`, and
  `Retry-After` exposed. No credentials: a request with `credentials: 'include'` fails.
- Sent on: `Accept`, `Authorization`, `Content-Type` and `Git-Protocol`, under `User-Agent:
  git/nuee.io-relais`; never a cookie, the visitor's address, `Origin`, `Referer` or Cloudflare's
  headers (`cf-*`, `x-forwarded-*`); Cloudflare adds its own `CF-Worker: nuee.io` to every request
  a Worker makes. Given back: the status, `Content-Type` and `Retry-After`, with `Cache-Control:
  no-store`, `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that sandboxes it;
  never `Set-Cookie`, nor `WWW-Authenticate`: on nuee.io's own page, a 401 with it would have the
  browser ask for a password itself (isomorphic-git reads the status alone).
- The bodies stream both ways, never held. The relay follows no redirect: one is passed on,
  rewritten to come back through the relay, only when it leads to one of these requests (as
  GitLab's address without `.git` to the one with it); any other gives 502.
- It sees the projects and sign-ins that pass through it, in transit, and keeps nothing: it writes
  nothing, and the Worker keeps no log of each request (`wrangler.jsonc`:
  `observability.logs.invocation_logs` false; Workers Logs would record each one with its address
  and headers), its errors alone. `RELAIS_LIMITE`, Cloudflare's rate limiting by the visitor's
  address (counted over a minute, in each of Cloudflare's locations), lets each address have 600
  requests a minute sent on, then answers 429.
- Cloudflare's free plan: 100,000 requests a day to the Worker, shared with the site's own
  (`/download`, `/version.json`, the 404s; the static files don't count), 10 ms of CPU each (the
  relay's own code takes about 10 µs a request, timed in Node; the bodies are streamed by the
  runtime, not by its code), 50 subrequests (it makes one). Signing in polls every 5 s and a push
  or a fetch is 2 to 4 requests, so a share is a few tens, and the plan covers thousands a day;
  past it, until midnight UTC, Cloudflare answers its error 1027 instead of running the Worker (the
  relay, `/download`, the 404s), while static files, which it doesn't count, are still served.
  Cloudflare refuses a request body over 100 MB (413) before the Worker runs. A push sends at once
  every version the repository doesn't have yet, each compressed (a project to about a quarter of
  its size), so a project with many versions not sent yet, or a very large one, can be too much for
  the relay where the desktop application would send it (GitHub refuses a file over 100 MB
  anyway); receiving (clone, fetch) has no limit.
- For the checks alone, `RELAIS_ESSAI`: an address on this computer (`http://127.0.0.1:<port>`)
  that receives `/<host>/<path>` instead. It is read only when the relay itself is reached on this
  computer (`wrangler dev`), never on nuee.io, and no configuration sets it.

## How it matches the stored results

Checked on 944 fitted models from 133 distinct `.usp` projects (file versions v10, v11 and
v16/17). Thresholds are 1e-4 for the fit and 1e-3 relative for derived statistics.

- **Scaled data, rebuilt from raw values:** all 944 match.
  - UV / Pareto / centring weights are computed over the workset observations.
  - The power transform is supported.
  - Qualitative variables expand into 0/1 terms.
  - A cross term is the product of its already-scaled factors, then scaled again.
- **PLS, complete data:** R2X, R2Y and scores match in 222/222 models.
- **With missing values:** 586 of the corpus's 590 PLS models match (R2X, R2Y, scores, loadings, VIP, coefficients), every PCA's R2X, and the scores and loadings of 107 of the 111 PCA models (on the corpus of 921 refitted models from 130 distinct projects).
  - NIPALS skips missing cells.
  - The correction factor is capped at 3.
  - **A model from a `.usp` file follows the NIPALS of the file's software** (`nipals.R`, since 1.0; `version_origine`, which the converter records, set: the model as read, or one derived from it). With missing values NIPALS can converge very slowly, not converge or have several solutions, and the stopping rule and the start decide the result. Each stored W, P, T, C and U is a NIPALS iterate under these rules to the file's rounding (1e-7), the same for versions 10, 11 and 13+: it stops when u (t for a PCA) changes by less than 1e-5 relative, or after 200 iterations (`TOLERANCE_FICHIER`, `ITERATIONS_FICHIER`: the threshold fits the 812 PLS and 474 PCA components of the corpus, copies included, where the stopping iteration can be told apart, but for a few whose criterion is within 0.3 % of 1e-5, rounding noise); it starts from the first column of largest sum of squares, within 1e-9 (`colonne_depart`: UV-scaled Y without missing values all have N − 1, and Nuée's `which.max` picked the one rounding made largest); each component's cross-validation rounds start from the full model's w (`composante_pls`'s `w0`, which gives back the stored rounds `cvW`); observations without any X value are perfectly fitted from the 1st component on (`residus_sans_x`: their Y residuals are 0, so the next components are fitted without them) and, in versions 10 and 11, perfectly predicted at the 1st component of the cross-validation; version 10 gives an X term without any value the w and p of the term before it (`reporter_vides`). Before 1.0, the 2003 projects' données M7 found another of its solutions, touspassereaux M8's 2nd component (the 200th iteration) and the files' validation rounds went elsewhere, and 21 models of version 11 (oppg_pr_2009) kept observations without X in their later components. Nuée's own models keep its rules (1e-10, 2,000 iterations, `which.max`, a cold start in each round), more precise.
  - Not reproduced: four PLS models of one version 11 project (PORQ ANALYSES reg pls), whose single Y has missing values: the software counts the observations without y in the X weights as if their Y residual were ±0.99 (the sign alternating from one to the next), at every component; nothing in the data gives that value, and no other file has a model like it. Every version 10 model with missing Y matches (17).
- **Derived statistics:**
  - Eigenvalue (= R2X·min(N, K)), T2, T2Crit, DCrit, VIP, coefficients and RMSEE match in every complete-data model.
  - The stored absolute DModX, and the weighted DModX, match in 264 of 267 complete-data models.
- **Signs:** models read from a `.usp` are oriented like the stored solution.
- **Coefficients and w\* with missing values** (since 0.9.9): W\* is such that the scores of complete observations are T = XW\*, w\*_a = w_a − Σ_{b<a} w\*_b (p_b′w_a), in the order the components are removed (an OPLS's orthogonal ones first: `statistiques.R`, `coefficients_pls` and `ordre_retrait`). Without missing values that is W(P′W)⁻¹; with them p_a′w_a is no longer 1, and W(P′W)⁻¹, which the engine and the converter used up to 0.9.8, put the coefficients off by up to 0.044. The recursion gives the coefficients and intervals the software that wrote the files exports itself: 35 of 35 models of a real project with missing values, and 3 of a second one, to 1e-6. The converter computes the "stored" coefficients and their intervals from the file's W, P, C and cross-validation rounds (`usp_extract.py`: `_coefs`), so `verifier_references.R` compares two computations of the same formula, not the software's own values.

Known differences:

- **Q2, and everything that comes from the cross-validation** (Q2 per variable, RMSEcv, CV-ANOVA, the cross-validated classification and ROC, jack-knife intervals, automatic fitting): three ways to validate (`validation_croisee.R`: `mode_validation`), the first the default for every model, imported ones included.
  - Observations go to 7 groups in turn (observation i to group i mod 7), or one group per value of an ID or a variable. Each group is predicted by a sub-model fitted without it, through the path of new observations (`prediction.R`): what the engine computes from the observations — centres, MSC's mean spectrum, 0/1 terms, cross and square terms — is computed again on the other observations; transformations and stored weights stay fixed. The sub-model has the same number of components (fewer if its observations have no variation left) and no cross-validation of its own.
  - **Centres recomputed, full model's weights** (`centres`, the default since 0.9.8): the scaling weights are the full model's. The sub-model knows nothing of the held-out group's Y (not even its mean); X's standard deviations don't depend on Y (with a single Y, its weight doesn't change the predictions), and nothing is rescaled on fewer observations, so nothing blows up. On the test corpus (916 models), the median absolute difference from the stored Q2(cum) is 0.003 for PLS models with more than 200 observations, 0.010 from 50 to 200, 0.10 from 20 to 49 and 0.22 below (Nuée's Q2 is lower in 81 to 100 % of these models below 200 observations), 0.04 for PCA; no model falls below −1.
  - **Centres and weights recomputed** (`sans_fuite`, the default from 0.9.0 to 0.9.7): the weights too. Up to 0.9.7, 18 of the 944 models lost more than 1: a variable that varies on about one observation, which the scaling of the other observations blew up. Since 0.9.8 a UV or Pareto term whose standard deviation on a sub-model's rows is under 10 % of the full model's keeps the full model's weight (`SEUIL_ECART_VC`); on four real projects of 447 models, that took the models below Q2 = −2 from 29 to 9 (the worst was −8e11). On the corpus: 0.003, 0.015, 0.11 and 0.51 by the same bins.
  - PLS, PLS-DA: PRESS is the sum over the left-out observations of ((y − ŷ)·w)², w being the full model's scaling weight of y, so it is in the full model's scaled units; Q2(cum) = 1 − PRESS(a)/SS, Q2 = 1 − PRESS(a)/PRESS(a−1) with PRESS(0) = SS. The empty model (`fin_validation`: `q2_vide`, since 0.9.9) predicts each left-out group by its sub-model's centre of Y, the mean over the other observations: its PRESS is PRESS0 and its Q2 1 − PRESS0/SS, below 0 when the groups differ; the gain is (Q2(cum) − q2_vide)/(1 − q2_vide) = 1 − PRESS(A)/PRESS0 (PLS and OPLS, the first two ways only; the honest Q2 of a hierarchical model has its own). OPLS: the same, the sub-model an OPLS with the same predictive and orthogonal components; row r of the components table is predicted with min(r, Ap) predictive components after max(0, r − Ap) orthogonal ones. PCA: each cell is predicted from its observation's scores computed without the cell's group of variables (variables also go to 7 groups in turn), treated as missing values.
  - **Full model's centres and weights** (`complet`, "like SIMCA" in the interface): the validation of the stored values. Each PCA or PLS component is validated on the full model's residuals, one component fitted without each group, and Q2(cum) = 1 − ∏(1 − max(Q2, −0.1)). That gives back the stored Q2 and Q2(cum) of 805 of the 809 PLS models (220 of 220 without missing data; the four others are the version 11 project whose fit differs, above), the coefficients' jack-knife intervals of 805 of 809, all 403 PLS models of the 2003 projects, and 441 of the 443 PLS models with stored results of four real projects (the two others have a round with no variation left, where the stored value comes from rounding errors). PCA: 0.018 off in median (the files' exact method isn't published). Its Y predicted in cross-validation (RMSEcv, CV-ANOVA, classification) comes from sub-models fitted without each group on the full model's matrices: the fitted Y of a − 1 components plus the validated component a, an earlier draft, made pure noise significant in CV-ANOVA 18 times out of 20. At small N this validation inflates Q2: on pure noise with 20 variables, it gave a median Q2(cum) of 0.98 for an automatic OPLS-DA of 6 observations and 0.45 for a 2-component PLS; the left-out row of a centred matrix is minus the sum of the training rows, so enough components "predict" it (a 6-observation PLS with 5 components had Q2 = 1.000). The two others keep medians below 0 (`verifier_validation.R`).
- **OPLS:** none of the projects has an OPLS model, so it is checked against theory and against a second writing of the published algorithm (`verifier_opls.R`), not stored results. With one predictive component its fitted values equal PLS's to 1e-14, and its scores are orthogonal. With several (several Y, or OPLS-DA with more than two classes), each orthogonal weight is the first loading made orthogonal to the space of the weights X'y of each column of Y (Trygg and Wold, 2002, OPLS for several Y), so the orthogonal scores are unrelated to Y; on complete data they match the second writing to 1e-8 and To'Y = 0. (0.8.0 made them orthogonal to the PLS weights instead, which left the orthogonal scores correlated with Y, up to a cosine of 0.1 on the example data.)
- **Standalone R scripts:** every model of the exported `.usp` projects under 20 MB (1,583 models from 207 files: 157 PCA, 926 PLS, 500 PLS-DA; 1,181 with missing values, 64 with cross terms) was exported. Each script, run without the engine, gives the engine's R2/Q2, scores, T2, DModX, limits, VIP, coefficients, CV-ANOVA and classification to 1e-8. That is the check `ecrire_script()` runs before writing.
- **Transform suggestions:** the published rule doesn't say whether both the skewness and the Min/Max criteria are needed; the app requires both.
- **Autofit:** the published rules, applied to the Q2 and Q2V of the validation chosen; with the first two, the number of components can differ (the example's PLS gets 7 instead of 4). PCA's significance limit isn't published, so the engine uses a degrees-of-freedom limit instead.
- **Rank:** a component is refused when what is left of X (or of Y) is below 1e-12 of its sum of squares at the start: a model can't have more components than its data's rank ("Component 5 is not possible…" instead of components of R2X 1e-32, or a singular matrix).
- **HCA:** this is exact Ward linkage. Every pair of leaves joined first matches the stored tree, but its top merges differ.
- **Jack-knife intervals:** over the 7 sub-models of the cross-validation (signs aligned with the full model). Validated with the full model's centres and weights, the coefficients' ones match the stored ones (above), and the software's own exports (half-width = t(0.975, G − 1) × its "cvSE"); with the other two, they differ. The VIPs' intervals match its exports for one-component models only: with two components or more it weights each round's components in a way that isn't published (neither the full model's explained SSY nor each round's, nor full sub-models', reproduce it; off by up to 0.4 in SE on a real project).
- **VIP cut-off:** the app's own method. It takes the largest drop in the sorted VIPs near Wold's 0.8 rule of thumb. The usual guidance only says VIP > 1.

## Speed

On a 9-component PCA of 797 × 58 values with 28 % missing, fitting takes about 1.7 s, most of it
in the cross-validation (7 sub-models, each predicting its left-out observations once per group
of variables). PLS models of the same size take well under a second.

`moteur/tests/banc_vitesse.R` times the engine through the server's requests, as the interface
sends them (JSON both ways), on simulated data of three sizes, `petit`, `moyen` and `grand`:

- near-infrared spectra of 100 × 500, 500 × 2,000 and 2,000 × 2,000, opened from CSV; PCA, PLS,
  PLS-DA and OPLS with the number of components chosen by 7-group cross-validation, after SNV and
  a first Savitzky–Golay derivative; a PLS's permutation test (100 permutations, not at
  2,000 × 2,000), its DModX, T², contributions and CV-ANOVA; the JSON of a model's views;
- field surveys of 2,000, 5,000 and 20,000 rows: a mixed model and a GAM with a random site effect,
  validated by site;
- tables of 1,000, 10,000 and 100,000 rows opened from CSV and .xlsx, with their Data view;
- a spectra project with 10 fitted models (`petit` and `moyen`), saved, opened again and its
  models refitted, as when the interface restores the session;
- the AIC selection and the block contributions of the surveys' mixed model and GAM; a random
  forest (500 trees) and boosted trees (2,000 trees at most) on the same surveys;
- communities of 60, 200 and 600 relevés of 30, 50 and 80 species: PCoA and NMDS with the X
  fitted to their axes, PERMANOVA, a Mantel test and its correlogram, indicator species, an RDA
  and the tests of its axes and terms, each with 999 permutations;
- TRIM on 50, 200 and 800 sites counted over 12, 20 and 25 years: model 3 with a covariate, and
  model 2 with its changepoints chosen stepwise;
- distance sampling with covariates (the observer and the wind; half-normal and hazard-rate keys)
  on 22, 70 and 210 transects.

It is not a check (GitHub doesn't run it): each case runs 3 times from the same state, and the
median is printed.

```bash
Rscript moteur/tests/banc_vitesse.R                                    # all of it: the cases of 1.0 about 30 min (2.5 h before 1.0), those added since over half an hour more
Rscript moteur/tests/banc_vitesse.R --tailles=petit,moyen --cas=pls    # some sizes, the cases whose name matches
Rscript moteur/tests/banc_vitesse.R --moteur=<another copy of Nuée> --garder=<folder>
Rscript moteur/tests/banc_vitesse.R --comparer=<folder>                # this engine's results against those kept
```

`--comparer` says for each case `identique` (`identical()`), `1e-12` (`all.equal()` to 1e-12) or
the first difference. The other options are `--repetitions=3`, `--temps=<file.csv>`,
`--travail=<folder>` (the files the cases write and open, kept from one run to the next) and
`--profil=<folder>` (`Rprof` on each case's first run). The times move with whatever else the
computer runs: compare two versions in the same conditions.

The shortcuts, each checked against the computation it avoids by `verifier_vitesse.R`:

- NIPALS (`nipals.R`): `crossprod` instead of transposing, a mask without missing cells left out
  of the products, and R's scan of each product for NaN skipped when the data are finite
  (`produits_sans_verification`: the same BLAS call);
- spectra preprocessed once per model: the steps that work one spectrum at a time (all but MSC:
  `spectres_par_ligne`) give each cross-validation group its rows of the full model's spectra
  (`pretraiter_bloc`); a permutation test, which permutes only Y, computes the X side of its
  models and of their cross-validation once (`cote_x_modele`, `tours_x_validation`);
- the automatic fit keeps the model it computed instead of fitting it again (`modele_tronque`;
  an OPLS from the kernels it kept, `noyau_reduit`): NIPALS computes the components one after
  the other;
- the data's rows and columns looked up once for all of a block's terms (`valeurs_bloc`,
  `definir_modele`); a project's observations and its models' terms written in one go when it
  is saved (`json_observations`, `json_termes_modeles`: the same file, byte for byte);
- the views (`panneaux.js`): only the spectra drawn and the Data view's columns shown are asked
  of the engine; tables drawn by slices of 20,000 cells; more than 5,000 points drawn by WebGL
  (`scattergl`);
- a block's simple terms scaled together (`construire_bloc`: `echelle_simples`), each column's
  mean and standard deviation computed by `mean()` and `sd()` as `echelle()` computes them (a
  stored or unknown scaling keeps the term-by-term path); the left-out rows' block skips the
  weighting it doesn't use, and the cross-validation's sub-models share the full model's
  (`facteurs_ponderation`);
- boosted trees (`boosting.R`): each tree made by rpart's C function with the arguments
  `rpart()` gives it, and only the parts of its result the boosting reads (`arbre_rpart`); the
  first trees are also made by `rpart()`, up to the first with a split, and the C function is used
  only if it gave them identically (otherwise `rpart()` makes every tree); the bag draw with half
  the operations per observation (`tirage_sac`). Also checked by `verifier_boosting.R`;
- distance sampling: the functions `integrate()` evaluates take the parameters' indices once, and
  for a key alone the key itself from `cle_detection` (`k × 1`, exactly), without
  `detection_distance`;
- TRIM: the inverse of each site's serial correlation computed once per ρ and per pattern of
  observed times (`inverses_trim`), for the GEE's equations and the score test of each changepoint
  the stepwise selection tries.
